# ADO Feed Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Herdr "Feed" of ADO things that need the team lead: PRs to review,
the team's failed builds, and work items newly assigned to him. Resolve state
lives in SQLite. A popup and a count on the ADO button announce new items.

**Architecture:**
- `feed.py` (Python, stdlib) owns ADO fetching, the SQLite database and the
  resolve actions. It is built in three layers:
  - a pure state engine;
  - fetchers that turn ADO responses into observations;
  - a CLI with `sync` / `list` / `resolve` / `unresolve`.
- `ado-feed/main.js` renders the feed and shells out to `feed.py`.
- my-tabs runs `feed.py sync --notify` every 3 minutes for the popup and the
  badge.

**Tech Stack:**
- Python 3 stdlib (`sqlite3`, `urllib`, `unittest`).
- Herdr JS mods (gpui-kit / gpui-base, the `herdr` module).
- ADO REST 7.1 through `standup.py`'s `Ado` client.

**Spec:** `docs/superpowers/specs/2026-11-16-ado-feed-design.md`

## Global Constraints

- **Python:**
  - stdlib only, run as `python3 -I <script>`;
  - output is one JSON object after a marker line (`@@ADO-FEED@@`), like
    `standup.py`.
- **Reuse `ado-standup/standup.py`:**
  - load it by path with `importlib`, from `Path(__file__).resolve().parent.parent / "ado-standup" / "standup.py"`;
  - reuse `Ado`, `token`, `az_bin`, `default_org`, `team_info`, `wiql`,
    `state_categories`, `person`, `q` and `RESOURCE`;
  - don't copy them.
- **Settings:** come from `<home>/addons.json`; every caller passes
  `--home <appHome()>`:
  - project = `ado.standup.project` (required);
  - team = `ado.feed.team` or else `ado.standup.team` (required);
  - org = `ado.org` or else `default_org`.
- **Database:**
  - location: `<home>/ado-feed.db`;
  - open every connection with `timeout=10`;
  - make every write a `BEGIN IMMEDIATE` transaction;
  - store all times as ISO-8601 UTC strings, but compare them only after
    parsing, never as strings (ADO sends 7-digit fractions and `Z`);
  - delete resolved rows older than 30 days on each sync.
- **Development safety:**
  - never approve a PR or change a work item in the real org;
  - live checks may only run read-only `sync` / `list`.
- **Wording and UI:**
  - user-facing copy follows the spec;
  - the toggle tooltips are "Approve and resolve" (a PR without his approval),
    "Close and resolve" (a work item in Pending QA), "Resolve" (anything
    else), and "Reopen" (a resolved row);
  - kind colors reuse the standup palette: PR `#9085e9`, build `#d03b3b`,
    work item `#3987e5`;
  - the feed dialog is `{"kind":"dialog","width":0.8,"height":0.8}`;
  - menu height 270;
  - the key is `cmd-shift-a` (it's unused in `keys.json` and my-main).
- **Tests:** `python3 -m unittest discover -s azure-devops/tests/ado-feed`.
  The existing suites must stay green:
  - `node --test "azure-devops/tests/ado-prs/*.test.mjs"`;
  - `python3 -m unittest discover -s azure-devops/tests/ado-standup`.

## Rulings made while planning

- **Work items that count as "newly assigned":** only items whose assignment
  to him happened in the last 14 days. Without this cut, the first run would
  list every item he has ever held, because "1 week" shows every unresolved
  item whatever its age. If this is wrong, the cost is one constant
  (`WI_ASSIGNED_DAYS`).
- **How long builds are followed:** failed runs are fetched for 14 days. A
  group with no runs in that window drops out and auto-resolves. If this is
  wrong, the cost is one constant (`BUILD_DAYS`).
- **Auto-resolve means "missing from this sync's observations"**, and it
  applies only to kinds whose fetch succeeded.
- **The team group counts as one of his groups:** reviewer groups matched for
  the lead are the team's member groups plus the team itself
  (`[<project>]\<team>`). The match is case-insensitive, on the last `\`
  segment, as in the standup.

## Review Focus

1. **A fetch fails for one kind** (a timeout on builds, for example). That
   kind's open rows must stay open. Absence of data isn't resolution. → Task 1
   test `test_failed_kind_does_not_auto_resolve`.
2. **ADO timestamps with 7-digit fractions** (`2026-11-16T10:00:00.1234567Z`)
   next to Python-written ones. Ordering must be by parsed time. → Task 1 test
   `test_parse_time_handles_ado_fractions`.
3. **my-tabs and the open feed sync at the same moment.** No duplicate popup and
   no lost rows. → Task 3 test `test_concurrent_syncs_notify_once`.
4. **A resolve whose ADO call fails** (no permission, network). The row stays
   open and the error reaches the UI. → Task 3 test
   `test_resolve_failure_leaves_row_open`.
5. **ado-feed isn't installed, or the settings are missing.** my-tabs must stay
   silent: no popup, no badge, no error loop. → Task 5 step 2 guard plus the
   manual check.

### Task 1: State engine and database (`feed.py`, no network)

**Files:**
- Create: `azure-devops/mods/ado-feed/feed.py` (the engine section only; later
  tasks add to it)
- Test: `azure-devops/tests/ado-feed/test_engine.py`

**Interfaces:**
- Produces:
  - `parse_time(s: str) -> datetime`: aware UTC; accepts `Z`, offsets, and 0–7
    fraction digits.
  - `iso(dt) -> str`.
  - `connect(path: str) -> sqlite3.Connection`: creates the schema if missing.
    The schema:
    - `items(key TEXT PRIMARY KEY, kind TEXT, title TEXT, sub TEXT, url TEXT,
      ref TEXT /*json*/, event_at TEXT, event_text TEXT, action TEXT,
      first_seen TEXT, resolved_at TEXT, resolved_by TEXT, note TEXT,
      notified INTEGER)`;
    - `meta(k TEXT PRIMARY KEY, v TEXT)`.
  - An observation is a dict with these keys:
    - `key`, `kind` (`pr` | `build` | `wi`), `title`, `sub`, `url`;
    - `ref` (a dict, opaque to the engine);
    - `event_at` (ISO), `event_text`;
    - `action`: the ADO action a resolve would take, `approve` | `close` |
      `none`.
  - `apply_sync(conn, observations: list[dict], ok_kinds: set[str], now: datetime) -> dict`.
    It returns `{"new": [row...], "first": bool}`, where `new` holds open rows
    with `notified = 0`. Its rules:
    - Baseline (`meta.baseline` absent): insert everything open with
      `notified = 1`, set `meta.baseline`, and report `first = True`.
    - A new key is inserted open with `notified = 0`.
    - For an existing open row, update the display fields; `notified` is
      untouched.
    - An existing resolved row whose observation's `event_at` is later than
      `resolved_at` is reopened: `resolved_at`, `resolved_by` and `note` are
      cleared and `notified = 0`. Otherwise only the display fields update.
    - An open row whose kind is in `ok_kinds` but whose key is missing from the
      observations is resolved with `resolved_by = 'auto'`, at `now`.
    - Delete resolved rows whose `resolved_at` is more than 30 days before
      `now`.
    - Set `meta.last_sync`.
  - `mark_notified(conn, keys: list[str])`.
  - `open_count(conn) -> int`.
  - `list_rows(conn, window: str, resolved: bool, now) -> list[dict]`, with
    window `24h` | `48h` | `1w`:
    - An open row is shown when the window is `1w`, or its `event_at` is
      within the window.
    - A resolved row is shown only when `resolved` is set and its `event_at`
      or `resolved_at` is within the window.
    - Sort by `event_at`, newest first.
    - `ref` comes back as a dict.
  - `set_resolved(conn, key, by: str, note: str, now)` and
    `set_unresolved(conn, key)`. `set_unresolved` also sets `notified = 1`, so
    reopening doesn't trigger a popup.
  - `summary(new: list[dict]) -> dict | None`: returns
    `{"title": "3 new in ADO", "body": "2 PRs to review · 1 failed build"}`.
    The labels are, singular and plural:
    - `pr`: "PR to review" / "PRs to review";
    - `build`: "failed build" / "failed builds";
    - `wi`: "item assigned to you" / "items assigned to you".
    The parts are in the order pr, build, wi. Returns `None` when `new` is
    empty. The title is "1 new in ADO" for one item.

### Task 2: Fetchers (ADO → observations)

**Files:**
- Modify: `azure-devops/mods/ado-feed/feed.py` (add the standup import and the
  fetchers)
- Test: `azure-devops/tests/ado-feed/test_fetch.py`

**Interfaces:**
- Consumes the Task 1 observation shape, and `parse_time` / `iso`.
- Produces:
  - `standup` (the module, loaded by path).
  - `me(ado) -> {"id", "name", "mail"}` from
    `/_apis/connectionData?api-version=7.1-preview.1`, using
    `authenticatedUser.id`, `providerDisplayName` and
    `properties.Account.$value` (lowercased).
  - `pr_observations(ado, me, groups: set[str], now) -> list[obs]`. `groups`
    holds lowercased last segments. The fetch:
    - list `/{project}/_apis/git/pullrequests?searchCriteria.status=active&$top=1000&api-version=7.1`;
    - skip drafts;
    - for each PR, find his reviewer entry (`id == me.id`, or the uniqueName
      matches his mail) and his group entries (`isContainer` and the last
      segment in `groups`);
    - skip the PR if he has neither.
    - Fetch iterations (`.../pullRequests/{id}/iterations?api-version=7.1`;
      the latest `createdDate` is `push_at`) and threads (`.../threads?api-version=7.1`):
      - `comment_at`: the latest `publishedDate` of a non-system comment whose
        author id isn't his;
      - `vote_at`: the latest `publishedDate` of a thread where
        `properties.CodeReviewThreadType.$value == "VoteUpdate"` and
        `properties.CodeReviewVotedByIdentity.$value == me.id`.
    - Use a `ThreadPoolExecutor(8)` across PRs.
    - **Needs him** when either:
      - (he has a personal entry with vote 0, or he's only on it through a
        group) and no group entry he matched has vote ≥ 5 when he has no
        personal entry; or
      - his vote ≠ 0 and `max(push_at, comment_at) > vote_at` (when `vote_at`
        is missing, treat it as never).
    - **Output for a PR that needs him:**
      - `event_at` = max(`creationDate`, `push_at`, `comment_at`);
      - `event_text` names the latest of those three: "opened by <author>",
        "<name> pushed" (the latest iteration's `author.displayName`), or
        "<name> commented";
      - `action` = `approve` if his vote < 5, else `none`;
      - `ref = {"project", "repoId", "id", "vote"}`;
      - `sub = "!<id> · <repo> · <author>"`;
      - `key = "pr:<repoId>:<id>"`.
  - `build_observations(ado, now) -> list[obs]`. The fetch is one call:
    `/{project}/_apis/build/builds?minTime=<now-BUILD_DAYS>&statusFilter=completed&queryOrder=finishTimeDescending&$top=5000&api-version=7.1`.
    - Group the runs by (definition id, branch with `refs/heads/` stripped).
    - Drop a group if its newest run's result is `succeeded`.
    - Otherwise its failures are the `failed` / `partiallySucceeded` runs newer
      than its newest `succeeded` run.
    - **Output per group:**
      - `key = "build:<defId>:<branch>"`;
      - `title = "<pipeline> on <branch>"`;
      - `event_at` = the newest failure's `finishTime`;
      - `event_text = "failed N×"`, or "failed" when N is 1;
      - `sub = "#<number> · <requestedFor>"`, plus " · PR build" when
        `reason == "pullRequest"`;
      - `action = "none"`;
      - `ref = {"project", "build": <newest failed build id>}`.
  - `wi_observations(ado, me, now) -> list[obs]`:
    - WIQL `[System.AssignedTo] = @Me AND [System.ChangedDate] >= @Today-14`
      (via `standup.wiql`), then `workitemsbatch` for Title, Type, State and
      AssignedTo.
    - Drop an item when its state's category, from `standup.state_categories`,
      is `Completed` or `Removed`.
    - For each remaining item, read
      `/_apis/wit/workItems/{id}/updates?api-version=7.1`. Find the latest
      update whose `fields["System.AssignedTo"].newValue` is him (by id or
      uniqueName); `event_at` is that update's `revisedDate`. If no such update
      exists, use `System.CreatedDate`, with
      `event_text = "created by <name>"`.
    - Keep the item only if `event_at` is within `WI_ASSIGNED_DAYS = 14`.
    - **Output per item:**
      - `event_text`: "assigned by <revisedBy.displayName>", plus ", was
        <oldValue.displayName>" when an `oldValue` exists;
      - `action = "close"` when the state is exactly `Pending QA`, else
        `none`;
      - `ref = {"project", "id", "state", "type"}`;
      - `sub = "#<id> · <type> · <state>"`;
      - `key = "wi:<id>"`.
- The tests use a `FakeAdo` with `get(url)` / `post(url, body)`. It matches
  a dict of URL substring → JSON, and records calls.

### Task 3: CLI and resolve actions

**Files:**
- Modify: `azure-devops/mods/ado-feed/feed.py` (add `main()`, the commands and
  the actions)
- Test: `azure-devops/tests/ado-feed/test_cli.py`

**Interfaces:**
- CLI: `feed.py --home H <command>`, where `<command>` is one of:
  - `sync [--notify]`
  - `list --window 24h|48h|1w [--resolved]`
  - `resolve KEY`
  - `unresolve KEY`
- Each prints `@@ADO-FEED@@\n` followed by JSON:
  - **`sync`** prints `{"new": [...], "open": N, "first": bool, "summary": {...}|null, "errors": {kind: msg}, "project", "team", "generated"}`:
    - fetch the kinds in parallel;
    - `ok_kinds` is the kinds that didn't raise;
    - call `apply_sync`;
    - with `--notify`, `mark_notified` the returned `new` keys inside the same
      `BEGIN IMMEDIATE` as reading them, so two notifying syncs can't both
      report a key;
    - `summary` is `summary(new)`, but `null` when `first`.
  - **`list`** prints `{"rows": [...], "open": N, "last_sync": iso|null, "project", "team"}`.
    It makes no network calls.
  - **`resolve`** prints `{"row": {...}}` or `{"error": "..."}`. It acts
    first, then marks the row:
    - **`approve`:**
      - GET `/{project}/_apis/git/repositories/{repoId}/pullRequests/{id}/reviewers/{me.id}?api-version=7.1`;
        an HTTP 404 means vote 0;
      - if the vote is below 5, PUT the same URL with
        `{"vote": 10}`;
      - the note is "approved", or "already approved".
    - **`close`:**
      - GET `/_apis/wit/workitems/{id}?fields=System.State,System.WorkItemType&api-version=7.1`;
      - if the state is still `Pending QA`, take the first state of that type
        whose category is `Completed`, from `standup.state_categories`, and
        PATCH `/_apis/wit/workitems/{id}?api-version=7.1` with
        `[{"op":"add","path":"/fields/System.State","value":<state>}]` and the
        header `Content-Type: application/json-patch+json`;
      - the note is "closed", or "already <state>".
    - **`none`:** no call.
    - Then `set_resolved(by="me", note=...)`.
    - **On any exception:** print `{"error": msg}` and leave the row unchanged.
  - **`unresolve`** prints `{"row": {...}}`.
- Add the methods `Ado.put` and `Ado.patch` in `feed.py` through a small
  subclass `FeedAdo(standup.Ado)`. `patch` overrides `Content-Type`. Don't
  change `standup.py`.
- Missing settings print `{"fatal": "Set ado.standup.project and ado.feed.team or ado.standup.team in addons.json"}`.
